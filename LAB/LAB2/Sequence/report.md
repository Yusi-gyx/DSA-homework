## 代码补全任务
### C1
- `vector::grow()`
  算出倍增后的容量，然后为新容量分配一块内存，将原数组的数据复制到新数组中；然后删除原来的数组指针，将新分配的数组指针赋值给vector
- `vector::shrink()`
  先判断当前填充率是否需要进行缩容；然后计算缩小后的容量并重新分配内存，将原数组中的数据复制到新数组中，删除原数组指针并将新指针赋值给vector
- 需要注意的地方
  在计算更新后的容量时，由于`GrowthNum`和`GrowthDen`都是int类型，在计算过程中会出现舍入的问题，需要调整运算的顺序保证计算的正确性

### C2
- `PoolPtrLinkedList::insert()`
  参考了`PtrLinkedList::insert()`的实现，处理逻辑基本一致；不同的操作在于新的节点不是通过new动态分配得到，而是直接将已经分配好的节点从pool中取出来
- `PoolPtrLinkedList::remove()`
  同样参考`PtrLinkedList::remove()`函数的实现，处理逻辑基本一致；不同的操作在于删除节点不是通过delete，而是通过`free_node()`将节点重新放回到pool中
- `ArrayLinkedList::insert()`
  `ArrayLinkedList`使用了两种序号：链表序号和池内序号，一个节点的池内序号是确定的，所以在`next_`和`prev_`等数组中均通过池内序号存储相关信息；所以在进行操作之前需要获取相关节点的池内序号，后续操作的对象也是池内序号。处理逻辑和上面两种链表的逻辑大致相同
- `ArrayLinkedList::remove()`
  具体思路和`ArrayLinkedList::insert()`一样，实现逻辑和上面两种链表的逻辑大致相同

### C3 
- `UnrollLinkedList::split_chunk()`
  根据已有chunk计算分块后两块的大小，然后将chunk的后半段数据复制给新chunk；最后更新各个chunk之间前驱、后继的连接
- `UnrollLinkedList::try_merge()`
  先判断当前块是否满足合并的条件：是否有后继块、两个块的大小之和是否不超过块的最大大小；将后续块的数据复制到前一个块数据的尾部；调整各个块之间的前驱后继关系，最后删除后面的块
  
### C4
- `XorLinkedList::get_next()`
  每个节点的`xor_ptr`保存前驱地址和后继地址的异或值。已知前驱地址时，将它与当前节点的`xor_ptr`再异或一次，前驱地址会抵消，得到的就是后继地址。
- `XorLinkedList::remove()`
  先用`get_node()`找到待删节点和它的前驱，再用`get_next()`求出后继。对两侧相邻节点的`xor_ptr`，先异或待删节点的地址将它抵消，再异或新的邻居地址。删除首尾节点时更新`head_`或`tail_`，最后释放待删节点并将`size_`减一。
- `XorLinkedList::~XorLinkedList()`
  从头开始遍历，每轮先用前驱和当前节点解出后继，再释放已经用完的前驱节点。当前节点保留到下一轮，作为已知的前驱参与下一次解码。遍历结束后再释放最后一个节点。

### T1：Vector不同扩缩系数的性能
- 结论：
  * 选择2X倍率是对**扩缩容复制次数**和**预留空间大小**的综合考虑。该实验对不同倍率下（1.25X，1.5X，2X，3X）的向量中部插入/删除进行了测试，计算了平均每次操作耗时、扩缩容次数、峰值容量、重复复制操作次数。**操作平均开销**方面，各个倍率在同一规模下的表现相近，没有展现出很明显的性能差异，我认为是我的测试数据规模不够大（我的实验测试数据最大规模为$10^6$次插入/删除操作）；**扩缩容次数**方面，随着倍率增大，扩缩容次数很明显的下降，1.25X的次数是3X次数的4-5倍，与此相关的就是**重复复制次数**，倍率越高进行的复制移动就越少，1.25X的次数是3X的5-7倍；峰值容量方面，能够明显的看出，随着倍率增大峰值容量也迅速增大，3X的峰值容量大约是其他倍率的2倍。

### T3：块状链表各种操作的性能
- 结论：
  * 在同一数据规模下，块容量越大（分块数量越少），普通插入、普通删除、块拆分、块合并、按下标查找这些操作的性能越好，比如块容量为256的块状链表各操作的性能约是块容量64的2-3倍；我认为造成造成这一差异的原因是块容量越大，定位时经过的块更少，需要进行的顺序查找、数据复制等操作更少，所以均摊性能上会更好。
  * 测试中和上述操作性能表现相反的时头部增块和头部删块，原因是块容量更大时每次增加/删除块进行动态分配操作的耗时更大，因此块容量越大新增、删除块时性能越差。
  * 此外，我还进行实验对比了块链表和向量（2X倍率）、普通链表各操作的性能。在已知插入位置的情况下，链表的插入性能和块链表相当，而向量的插入性能远高于这两者；如果不知晓插入/删除/查找位置，由于链表需要进行逐个元素的顺序查找，其性能相比于另外两者非常差；随机查找操作方面，向量是做的最好的，性能远远领先于块链表和普通链表。
  * 块链表实际上是向量和链表之间的一个tradeoff，块链表顺序查找的次数没有链表那么多，动态操作时移动的次数没有向量那么多，所以静态和动态操作的性能分别有向量和链表的特点。

## 思考题
### E1
设连续进行了`n`次的`push_back()`，则一共进行了 $\log_{R} n$ 次扩容操作，第 $i(1 <= i <= \log_{R} n)$ 次扩容复制的次数为 $R^{i}$ ，所以`n`次`push_back()`的总花销为 $\sum_{i = 1}^{\log_{R} n} R^{i} = O(R^{\log_{R} n}) = O(n)$，因此均摊复杂度为 $O(n) \div n = O(1)$ 。

### E2
* 逐个`push_back()`时，`GCC`的`libstdc++`通常按 2 倍扩容,`MSVC STL`通常按约 1.5 倍扩容。
* `libstdc++` 取 $size + max(size, num(new_data))$，`MSVC STL` 取 $max(size * 1.5, size + num(new_data))$。
* 两者都保留删除后空出来的容量，而本实验实现会按填充率自动缩容。

### E3
在已知操作位置的情况下（比如头部插入/删除），链表的插入/删除速度远快于向量，因此链表完成操作后不需要移动其他已有元素的位置；但是在随机插入/删除的测试中，链表的性能是远低于向量的，因为链表需要进行一次顺序查找确定操作的位置，而链表的顺序查找是及其耗时的。

### E4
* `CPython`的 `collections.deque` 用的是固定大小的块组成的双向链表。在`CPython 3.14`中，每块有64个连续的槽位，存放 `Python`对象的引用，并通过前后指针连接相邻块。`deque` 直接记录左右端所在的块和块内下标。
* 和向量相比，头删省掉了整体搬移；和普通链表相比，多个元素共用一对链接；这个设计使得`deque`进行头尾部插删的性能很好，但是查找操作依然需要通过顺序遍历来进行，最坏情况下$O(n)$。

### E5
* 原理：将最后一个元素移动构造到需要删除的位置，然后将最后一个元素进行析构。
* 预期性能：每次删除操作都只需要移动构造一个元素、析构一个元素，每次操作的复杂度为$O(1)$。

### E6
实际项目中，选择数据结构时，可以先看各种操作的频率、数据规模，以及是否需要保留元素的相对顺序。按下标访问、遍历或尾插较多时，可以用 `Vector`。两端插删较多时，可以用 `deque`。如果已经拿到了指向目标位置的迭代器，双向链表可以在 $O(1)$ 时间内完成插删。若允许改变顺序，也可以用向量的末尾元素填补删除的位置。
