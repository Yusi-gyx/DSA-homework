### 代码 01

1. **最严重错误类型：Runtime Error**（未捕获的 `std::out_of_range`，SIGABRT，rc=134）。
2. **原因**：`play` 在消除后无条件调用 `play(left - 1)`。
   当被消除的同色块从序列最左端（下标 0）开始时，`left == 0`，于是递归到 `play(-1)`；
   函数开头 `char color = a.at(rank);` 对 `rank = -1` 求值，`at` 把 -1 转成
   `size_t`（18446744073709551615）后越界，抛出 `std::out_of_range` 并终止程序。
   `base.cpp` 中对应位置有 `if (l >= 0) play(l)` 的保护，01 删掉了它。
4. **发现方法**：对拍。用随机测例与 `base.cpp` 比较，01 在绝大多数测例上会异常退出（rc=134），
   第一轮就可能出现。
5. **测例构造**：让 3 颗同色珠恰好在序列头部形成并被消除：
   初始 `AA`，在 0 号位置插入 `A` 得到 `AAA`，整段从下标 0 开始消除，`left == 0`。

**最终测例（01.in）**

```text
AA
1
0 A
```

标准答案：空行。01 的运行结果：`terminate called after throwing an instance of 'std::out_of_range'`，rc=134。

### 代码 02

1. **最严重错误类型：Runtime Error**（`std::out_of_range`，SIGABRT，rc=134）。
2. **原因**：消除后代码用
   `int next = left; if (left - 1 >= 0) next = left - 1; play(next);`
   决定递归位置。当消除块从头部开始（`left == 0`）时，`next` 被设为 0 而不是停止递归。
   如果这次消除把整个序列消空，`play(0)` 开头 `a.at(0)` 对空串越界，抛异常终止。
   （`base.cpp` 在 `l < 0` 时直接不递归。）
4. **发现方法**：对拍。生成器会生成初始为空、或操作后序列被消空的情况；02 在这些测例上 rc=134。
   由于还要求“消除块在头部”，随机命中率比 01 低一些（见任务 2-1 统计）。
5. **测例构造**：同 01，让头部 3 颗同色被消除且整串清空，`left == 0` 后错误地 `play(0)`。

**最终测例（02.in）**

```text
AA
1
0 A
```

标准答案：空行。02 的运行结果：`basic_string::at: __n (which is 0) >= this->size() (which is 0)`，rc=134。

### 代码 03

1. **最严重错误类型：Time Limit Exceeded**。03 的功能逻辑经大量对拍（见任务 2-1）未发现错误，
   可以认为它是“正确但复杂度不达标”的版本。
2. **原因**：`std::string::insert/erase` 每次都要移动 O(n) 个字符，m 次操作总复杂度 O(nm)；
   在 n = m = 5×10^5 时约需搬运 3.75×10^11 字节，远超 1.5 s 时限。
   另外它和 01/05 一样用递归做连锁消除，但本题的递归深度不是主要问题，复杂度才是。
4. **发现方法**：复杂度分析 + 计时。在本地对最大规模的合法测例计时约 5.0 s（-O2），
   而 OJ 时限只有 1.5 s。
5. **测例构造**：取 n = 500000 的稳定初始串 `AABB` 重复 125000 次；
   m = 500000 次操作全部在 0 号位置插入交替的 `C`、`D`。由于每次插入颜色都与相邻珠子不同，
   不会发生消除，每次插入都要把整个字符串右移一位，使总搬运量达到上界附近。
   期望输出可以精确写出：把 50 万次插入逆序拼到初始串前面，即
   `"DC"×250000 + "AABB"×125000`（恰好 10^6 个字符）。

**最终测例（03.in）**：由下面的脚本生成（文件约 2.4 MB）。

```python
n, m = 500000, 500000
init = "AABB" * (n // 4)
with open("03.in", "w") as f:
    f.write(init + "\n" + str(m) + "\n")
    for i in range(m):
        f.write("0 " + "CD"[i % 2] + "\n")
```

标准答案：`"DC" * 250000 + "AABB" * 125000`。03 的运行结果：本地 -O2 约 5.0 s，
超过 1.5 s 时限（OJ 上应为 TLE；若 OJ 机器明显更快而未能复现，请以本报告的计时与复杂度分析为准）。

### 代码 04

1. **最严重错误类型：Wrong Answer**（该代码在别的测例上也可能异常退出，但 WA 更严重）。
2. **原因**：向左扫描写成了
   `while (left > 0 && a.at(left) == color) --left;`
   循环结束后没有 `left += 1`，而且边界条件用了 `left > 0`。
   于是 `left` 停在消除块左边第一颗**不同色**珠子上（或 0），
   `size = right - left` 比实际同色块长度多 1，`a.erase(left, size)` 会多删掉左边那颗珠子。
   若被删的块在序列中部，还会让后续操作的下标整体错位，可能进一步触发越界崩溃。
4. **发现方法**：对拍。随机测例中只要出现“消除块左边紧邻一颗不同色珠子”就会输出不同；
   gdb 中可直接看到 `left`、`size` 与定义不符（见任务 2-1.3）。
5. **测例构造**：最小化工具从随机错例化简得到：初始 `AB`，在 2 号位置插入 `B` 得到 `ABB`。
   正确结果中只有 2 颗相邻的 `B`，不应消除；04 的 `left` 从 1 被扫到 0，算出 `size = 3`，
   把 `A` 一起删掉，输出空串。

**最终测例（04.in）**

```text

1
2 B
```

标准答案：`ABB`。04 的输出：空行（WA，rc=0）。

### 代码 06

1. **最严重错误类型：Wrong Answer**（越界写入仍落在 `p` 数组内部，不会越出数组崩溃）。
2. **原因**：07~10 在 `play` 里都有“块过长就 `p2a(); a2p();` 重组”的保护，06 删掉了它。
   每个块的行容量是 `plen_bound = 4096`，插入时 `memmove` 会把块内后缀右移一位；
   当某块长度达到 4096 时，写入位置越过本行末尾，直接写进下一行——也就是相邻块的数据区。
   于是相邻块被改成别的字符，最终 `p2a()` 组装出的字符串与正确答案不同。
   由于 `m ≤ 5×10^5`，块长度最多增长到约 5×10^5，而 `p` 一共有 4096 行 × 4096 字节，
   写坏的区域仍在数组内部，所以实际表现是数据被静默写坏（WA），而不是越界到数组外崩溃。
4. **发现方法**：对拍 + 中间变量。随机生成“初始串很长（至少两个块）+ 大量位置偏向头部”的测例；
   用调试版打印 `plen[0]`，可以看到它从 4095 涨到 4096、4097，同时 `p[1][0]` 被覆盖。
   普通的均匀随机位置很难命中，需要专门的位置分布（见任务 2-1.2）。
5. **测例构造**：初始串 `"AB"` 重复到 2049 个字符（保证 `pn = 2`，即块 1 有数据）；
   然后做 2049 次“在 0 号位置插入”的操作，颜色按 `B, A, B, A, ...` 交替
   （每次都与当前首字符不同，保证不消除）。这样 0 号块从 2048 长到 4097，越过 4096 的边界，
   写坏 1 号块的数据。

**最终测例（06.in）**：由下面的脚本生成（11 KB）。

```python
init = ("AB" * 1025)[:2049]
ops = []
c = "B"
for _ in range(2049):
    ops.append("0 " + c)
    c = "A" if c == "B" else "B"
with open("06.in", "w") as f:
    f.write(init + "\n" + str(len(ops)) + "\n" + "\n".join(ops) + "\n")
```

标准答案：长度 4098 的字符串（`base.cpp` 输出）。06 的输出同样长，
但第 4098 个字符起就不一样（`base` 末尾是 `...ABABA`，06 是 `...ABABB`），WA。
调试版可以看到 `plen[0]` 达到 4096 后 `p[1][0]` 从 `A` 变成 `B`。

### 代码 07

1. **最严重错误类型：Runtime Error**（`size_t` 下溢后 `memcpy` 越界，`-O2` 下 Fortify 报
   `*** buffer overflow detected ***`，SIGABRT，rc=134）。
2. **原因**：左扫描在“跨过空块”时只跳一次：

   ```cpp
   if (l.second < 0 && l.first >= 0) {
       l.first--;
       if (l.first >= 0) l.second += plen[l.first];
   }
   ```

   正确写法是 `while`（06、08、09、10 都是 `while`）。如果 `l.first` 跳过去的那一块恰好
   长度为 0，`l.second` 仍然是 -1；下一次循环条件 `get(l) == ch` 就会读
   `p[l.first][-1]`，也就是**上一行的最后一字节**（行在内存里连续），
   而不是上一个非空块的最后一个字符。这个脏字节如果恰好等于待消除颜色，
   扫描就会把不存在的珠子算进消除区间。
   执行消除时 `plen[l.first] = l.second + 1`，当 `l.second == -2` 时得到 -1，
   赋给 `size_t` 变成 18446744073709551615；随后 `p2a()` 里
   `memcpy(&a[0], p[0], plen[0])` 搬运极大长度，直接崩溃。
4. **发现方法**：对拍找不到（见任务 2-1：1000 个随机测例 0 次失败），
   改用“中间变量 + 构造”的方法：先制造两个连续空块，并让 0 号块的行尾留下已知脏字节，
   再触发左扫描，打印 `plen[0]` 即可看到 `SIZE_MAX`。
5. **测例构造**（分三步）：
   - 初始 `"AABB"×1024`（4096 个字符，两个整块）；
   - 在 0 号位置插入 2048 个字符，插入序列按 `B,B,A,A` 循环——这样前缀仍然是 `AABB`，
     整串变成 `"AABB"×1536`。0 号块长到 4096，最后一次插入把 `p[0][4095]` 写成 `B`，
     并触发重分块（`p2a + a2p`），此后 `pn = 3`，每块 2048；
   - 在 3070 号位置插入 `B`（`AABB` 模式的“连锁引爆点”），一次连锁把整串消到只剩末尾的 `BB`，
     块状态变成 `plen = {0, 0, 2}`：0、1 号块为空；
   - 最后在 0 号位置插入 `B`：左扫描从 2 号块进入空块 1，`if` 只跳一次，
     读到 `p[1][-1] = p[0][4095] = 'B'` 这个脏字节，误判为匹配，消除区间覆盖全串，
     `plen[0]` 下溢，`p2a` 崩溃。

**最终测例（07.in）**：由下面的脚本生成（13 KB）。

```python
init = "AABB" * 1024
ops = ["0 " + "BBAA"[i % 4] for i in range(2048)]   # 2048 次前缀插入
ops += ["3070 B", "0 B"]                            # 连锁引爆 + 触发越界
with open("07.in", "w") as f:
    f.write(init + "\n" + str(len(ops)) + "\n" + "\n".join(ops) + "\n")
```

标准答案：空行。07 的运行结果：`*** buffer overflow detected ***`，rc=134。
调试版在最后一个操作后打印出 `plen = {18446744073709551615, 0, 0}`。

### 代码 09

1. **最严重错误类型：Runtime Error**（`size_t` 下溢导致 `memcpy` 越界，rc=134）。
2. **原因**：06/07/08/10 在执行消除时都有
   `if (l.first == r.first) { ... 块内消除 ... } else { ... 跨块消除 ... }`
   的分支，09 删掉了“块内消除”分支，所有情况都走跨块逻辑。当消除区间在同一块内时：
   - 先执行 `plen[l.first] = l.second + 1;`，把该块截断到消除区间左侧；
   - 再执行 `if (r.first < pn) { int len = plen[r.first] - r.second; ... plen[r.first] = len; }`，
     但 `plen[r.first]` 已经被上一步改小，而 `r.second` 仍是消除区间右端的下标，
     `len` 常为负；负的 `int` 赋给 `size_t` 的 `plen` 后下溢成极大值；
   - 最后 `p2a()` 用这个极大值做 `memcpy`，越界崩溃。
4. **发现方法**：对拍。只要出现“在同一个块内部消除，且消除块左边/右边有存活珠子”，09 就会崩溃；
   初始串没必要很长（`pn = 1` 即可）。
5. **测例构造**：初始 `ABBA`，在 2 号位置插入 `B` 得到 `ABBBA`。
   消除中间的 `BBB` 时 `l = (0,0)`、`r = (0,4)`，`l.first == r.first`，
   09 走跨块分支：`plen[0]` 先被改成 1，再算出 `len = 1 - 4 = -3`，写入后变成
   `0xfffffffffffffffd`。

**最终测例（09.in）**

```text
ABBA
1
2 B
```

标准答案：`AA`。09 的运行结果：`buffer overflow detected`，rc=134。

### 代码 10

1. **最严重错误类型：Wrong Answer**。
2. **原因**：跨块消除时清零中间块的循环写成了

   ```cpp
   for (int i = l.first; i < r.first; i++) plen[i] = 0;
   ```

   起点应为 `l.first + 1`。`l.first` 是左边界块，块里保存着消除区间左侧**保留下来的**珠子；
   从它开始清零会把左边界块整块丢掉。
4. **发现方法**：对拍。需要“消除区间触及块边界”的测例；在 `pn = 1` 时，
   只要消除区间在序列头部、右侧越过了块末尾（`r.first` 滚到 `pn`），也会进入这个分支，所以小测例即可触发。
5. **测例构造**：初始 `BAA`，先在 3 号位置插入 `A`：`BAAA` 消除末尾的 `AAA`，
   `r` 滚到 `pn = 1`、`l = (0,0)`，走跨块分支，`plen[0]` 被错误清零（本应保留 `B`）。
   此时 `alen = 1`，但 `p2a()` 只拷贝 0 字节，`a[0]` 还是初始串的 `B`，所以单独看第一次操作
   结果“碰巧正确”。再插入一次 `C`（位置 1）：正确结果 `BC`，但 10 的块长度信息已损坏，
   最终输出 `BA`。

**最终测例（10.in）**

```text
BAA
2
3 A
1 C
```

标准答案：`BC`。10 的输出：`BA`（WA，rc=0）。

> 注：若删掉第二次操作，10 的输出碰巧等于正确答案——这是因为 `p2a()` 拷贝 0 字节时，
> 全局数组 `a` 里还残留着输入缓冲区的首字符。必须保留第二次操作才能把错误暴露出来。

- `zuma_apply(s, pos, color)`：在 `pos` 插入后反复扫描并删除所有 ≥3 的同色连续段，
  与 `base.cpp` 的“插入点消除 + 连锁”等价；
- 初始串随机生成长度 `init_len ∈ [min_len, max_len]`，并强制不存在 3 连；
- 每次操作随机生成合法位置 `pos ∈ [0, len]` 和颜色，同时用模拟器算出最终答案；
- 可选随机模式：
  - `pos_mode`：`uniform` / `front`（偏头部）/ `back`（偏尾部）/ `edge` / `block`（取 2048 块边界附近）；
  - `color_mode`：`uniform` / `pair`（以 2/3 概率取插入点相邻珠子的颜色，更容易凑出同色块）；
  - `min_len`：控制初始串的最小长度。
- `gen.py` 输出的答案会写入 `ans` 文件，供对拍脚本交叉校验 `base.cpp`。

**对拍脚本 `duipai.sh`**。它把 `base.cpp` 与 `01~10` 全部编译到 `build/`，然后循环 N 轮：
每轮用 `gen.py` 生成一个测例和标准答案，先检查 `base` 与生成器答案是否一致（防止生成器写错），
再逐一运行被测程序，比较**退出码**和**标准输出**；异常退出（RE）或输出不同（WA）都会把测例保存到
`build/fail/`，文件名带代码编号和轮次，方便复现。

**统计脚本 `bench.py`**。复用 `gen.py` 的生成逻辑，对每份代码做多次独立试验：
从 `seed_base+1, seed_base+2, ...` 依次生成测例，记录**第一次**出错的轮次 k，
最后给出均值/标准差/最小/最大值。未在 K 轮内出错的试验记为“未发现”，不参与均值计算
（报告中会注明 found 次数和 K）。

**最小化脚本 `minimize.py`**。给定一个错例，反复尝试“删一条操作 / 删一个初始字符 / 合并两种颜色”，
要求 `base` 仍能正常结束且目标程序仍以相同错误类型失败，直到不能再化简，用于任务 2-1.3 的
“更简单的错例”。

**选取的代码**：01、02、04、05、08、09、10（7 份随机对拍统计），
另外对 06 做了位置分布对照实验，对 07 做了“随机对拍找不到”的负面结果记录，
对 03 做了功能性对拍（未发现错误，结论为 TLE）。共 ≥ 5 份，满足要求。

（按题目提示：生成器和对拍脚本的编写可以使用大语言模型辅助，但本报告中“错误原因—测例构造—gdb
分析—统计解释”部分是按上面的实验独立复核过的；每个最终测例都在本地用 `base.cpp` 验证了标准答案。）

### 1. 首次发现错误所需的对拍次数

统一配置：`alpha=2`，初始长度 `0~30`，操作数 `0~20`，位置均匀分布，颜色均匀分布，
每份代码独立试验 8 次，每次最多 K=100 轮。表中的“均值±标准差”只在发现错误的试验上统计。

| 代码 | 发现次数 | 首次失败轮次 均值±标准差 | 最小值 | 最大值 | 首次错误类型 |
| ---- | -------- | ------------------------ | ------ | ------ | ------------ |
| 01 | 8/8 | 1.2 ± 0.4 | 1 | 2 | RE |
| 02 | 8/8 | 3.0 ± 3.9 | 1 | 13 | RE |
| 04 | 8/8 | 1.1 ± 0.3 | 1 | 2 | RE/WA |
| 05 | 8/8 | 28.4 ± 26.1 | 2 | 71 | WA |
| 08 | 8/8 | 1.9 ± 1.4 | 1 | 5 | WA |
| 09 | 8/8 | 2.1 ± 1.6 | 1 | 6 | RE |
| 10 | 8/8 | 2.5 ± 1.9 | 1 | 6 | WA |

**分析**：

- **01 / 02 / 04 / 08 / 09 / 10** 平均都在 1~3 轮内被发现，原因是它们的错误会在“任何一次消除”时暴露：
  01/02 只要消除块碰到头部，04 只要消除块左边有不同色珠子，08 只要消完一次需要连锁，
  09 只要消除块在同一块内部，10 只要消除区间碰到块边界。小字符集下消除频繁，因此很快命中。
- **05** 的首次失败轮次明显偏大且方差很大（28.4 ± 26.1）。原因是它依赖一个**结构性条件**：
  初始序列必须为空行，概率约为 `1/(max_len+1) = 1/31 ≈ 3.2%`；若 m 恰好为 0 还不会暴露。
  首次命中轮次近似服从几何分布，均值约为 `1/p = 31`，和实测 28.4 吻合；方差大正是几何分布的特征。
- **错误类型的差异**：RE（越界/抛出异常）和 WA（删除范围算错、缺少连锁、块清错）都可能在
  第一轮出现，只要测例结构满足触发条件；真正决定“难不难发现”的不是 WA/RE 本身，
  而是触发条件是否常见（05 的空初始串、06 的块溢出、07 的空块状态）。
- **04 首次失败类型既有 RE 也有 WA**：同一个“多删一个字符”的错误，在小测例上通常直接输出不同（WA）；
  当错误删除导致后续操作的下标整体错位时，也可能越界崩溃。两者中 WA 更严重，最终测例选的是 WA。

**按错误根源分类看发现难度**：

| 类别 | 代码 | 触发条件 | 随机对拍难度 |
| ---- | ---- | -------- | ------------ |
| 边界/空序列漏考虑 | 01、02、05 | 消除触及序列头部、序列被消空、初始序列为空 | 前两者容易；05 需要“空初始串”这一稀有结构 |
| 下标/边界 off-by-one | 04、10 | 消除块左边有异色珠子、消除区间触及块边界 | 容易，1~2 轮 |
| 分支/循环条件写错 | 07、09 | 跨空块时只跳一次、同一块内消除 | 09 容易；07 极难（需要空块 + 行尾脏字节） |
| 漏考虑连锁消除 | 08 | 消除后左右合并成新的大于等于 3 的块 | 容易（小字符集），大字符集变难 |
| 不变量/资源约束遗漏 | 06 | 单块长度超过 4096 | 难，需要位置偏置和足够长的初始串 |
| 复杂度错误 | 03 | 任意大规模输入 | 靠复杂度分析和计时，不靠对拍 |

可见“WA/RE 的类型”与“发现难度”并不一一对应：01/02 一碰就崩，但 05 同样是 WA，
却要等一个概率约 3% 的结构；06/07 则几乎只能靠分析代码加定向构造。

### 2. 调整 n、字符集和随机方式后的统计

#### 2.1 字符集大小（alpha）

每份代码 8 次试验，K=100，其余参数同上（n∈[0,30]，m∈[0,20]，位置均匀）。

| 代码 | alpha=2 | alpha=3 | alpha=6 |
| ---- | ------- | ------- | ------- |
| 01 | 1.2 ± 0.4 | 2.8 ± 1.5 | 13.8 ± 15.3 |
| 02 | 3.0 ± 3.9 | 41.3 ± 27.7（7/8） | 23.7 ± 13.2（3/8） |
| 04 | 1.1 ± 0.3 | 1.0 ± 0.0 | 1.1 ± 0.3 |
| 05 | 28.4 ± 26.1 | 28.4 ± 26.1 | 28.4 ± 26.1 |
| 08 | 1.9 ± 1.4 | 4.4 ± 4.4 | 29.3 ± 22.0（7/8） |
| 09 | 2.1 ± 1.6 | 1.4 ± 0.5 | 3.0 ± 2.4 |
| 10 | 2.5 ± 1.9 | 5.0 ± 4.7 | 21.6 ± 12.9（7/8） |

结论：

- 字符集越大，越难凑出 ≥3 的同色块和连锁，所有依赖消除的代码都更难被发现；
  01（13.8）、08（29.3）、10（21.6）在 alpha=6 时明显变慢，02 只有 3/8 的试验能在 100 轮内命中。
- **04 对字符集不敏感**（始终约 1.0），因为它的触发条件只是“消除块左边有一颗不同色珠子”，
  这在小字符集和大字符集下都几乎必然出现。
- **05 与字符集完全无关**（三列数值相同），因为它的错误只取决于初始序列是否为空，
  和颜色分布无关。
- 09 在 alpha=6 时反而略慢（3.0），因为要同时满足“同一块内部消除 + 右侧有存活珠子”，
  大字符集下消除本身变少。

#### 2.2 初始长度 n 和位置/颜色分布

| 配置 | 01 | 02 | 04 | 05 | 08 | 09 | 10 |
| ---- | -- | -- | -- | -- | -- | -- | -- |
| n∈[0,5], m∈[0,5]（10 次试验） | 3.6±1.7 | 5.7±3.7 | 1.9±1.8 | 3.6±1.7 | 25.0±15.9 | 13.8±10.8 | 10.5±10.1 |
| n∈[0,30], m∈[0,20]（基线） | 1.2±0.4 | 3.0±3.9 | 1.1±0.3 | 28.4±26.1 | 1.9±1.4 | 2.1±1.6 | 2.5±1.9 |
| n∈[0,200], m∈[0,50] | 1.2±0.4 | 3.0±2.8 | 1.0±0.0 | 59.0±25.2（3/8） | 1.0±0.0 | 1.0±0.0 | 1.1±0.3 |
| n∈[0,30], m∈[0,20], color=pair | 1.4±0.7 | 1.8±0.8 | 1.4±1.0 | 28.4±26.1 | 2.4±1.5 | 2.2±1.2 | 1.8±1.4 |

结论：

- **n 很小**（≤5）时，08、09、10 明显变难（25.0 / 13.8 / 10.5）：
  连锁消除需要足够的长度（如 08 的 `A`+`BBB`+`AA` 至少要 5 颗珠子），
  同块内消除且右侧有存活珠子也需要 n≥4；
  而 05 反而更容易（3.6），因为空初始串的概率变成 1/6，这正是 `1/(max_len+1)` 的体现。
- **n 较大**（200）时，01/08/09/10 都几乎第一轮就失败（消除更容易发生），
  但 05 更难：空初始串的概率降到 1/201，8 次试验里只有 3 次在 100 轮内命中，
  其余被截断（因此 59.0 是“已命中样本”的均值，真实期望更大）。
- **color=pair**（偏向取相邻珠子的颜色）会显著提高 02 的命中率（3.0→1.8）、
  略微提高 08/10，说明“主动凑同色块”比纯均匀颜色更容易触发消除类错误。
- **05 的均值基本不随 n/m/颜色变化**，只随 max_len 变化——这验证了它的错误根源是
  “初始序列为空”这一单一条件，而不是随机消除过程。

#### 2.3 针对分块实现的位置分布（06 / 07）

06 需要某个块长到 4096 以上，随机均匀位置很难做到（插入被分散到各块）。
固定 `alpha=26`（几乎不发生消除）、`n∈[2500,3000]`、`m∈[0,3000]`，对 06 做 5 次试验、K=20：

| 位置分布 | 发现次数 | 首次失败轮次 均值±标准差 |
| -------- | -------- | ------------------------ |
| `front`（偏向头部） | 5/5 | 2.4 ± 1.4 |
| `uniform` | 5/5 | 7.2 ± 3.2 |

`front` 让插入集中在前 1/16 长度的位置，持续把 0 号块撑大，所以更快命中；
`uniform` 把插入分散到整个串，需要更多轮次才能碰巧把某一块堆到 4096。
这也说明**“针对实现的弱点设计位置分布”比单纯增加轮数更有效**。

07 的错误需要极特殊的状态（连续空块 + 行尾脏字节），固定 `alpha=2`、`n∈[0,9000]`、`m∈[0,6]`，
`uniform` 和 `block`（2048 边界附近）各跑 5 次试验、每次 K=100，**共 1000 个测例均未发现错误**。
只能通过分析代码 + 手工构造状态复现（见任务 1 的 07 小节），这也说明它的隐藏程度远高于其它代码。

#### 2.4 如何构造更容易触发错误的测例

1. **小字符集**（2~3 种颜色）能显著提高消除和连锁的频率，是发现大多数 WA/RE 的首选。
2. **颜色分布偏向相邻珠子**（`color=pair`）比均匀颜色更容易凑出同色块，尤其对 02、08、10。
3. **位置分布要针对实现**：分块实现在块边界/头部附近插入更容易触发越界和空块；
   对 06 使用 `front` 后首次失败轮次从 7.2 降到 2.4。
4. **n 要足够大**：连锁和“同块内消除 + 右侧存活”需要长度；对 06 还需要 n>2048 才能有第二个块。
5. **不要指望均匀随机发现所有错误**：05 依赖空初始串（概率 1/(n_max+1)），
   06 依赖单块长到 4096，07 依赖连续空块——这些都需要“定向构造”或“偏置分布”，
   在随机对拍里表现为均值大、方差大甚至长期 0 命中。

### 3. gdb / 中间变量调试、可解释性与更简单的错例

#### 3.1 代码 04：gdb 定位中间变量

用 `g++ -g -O0` 编译后，在 `04.cpp:17`（`a.erase(left, size);`）下断点，运行最终测例：

```text
$ gdb -q -batch -ex 'break 04.cpp:17' -ex 'run < 04.in' \
      -ex 'printf "a=%s left=%d right=%d size=%d\n", a.c_str(), left, right, size' \
      ./build/p04g
Breakpoint 1, play (rank=2) at 04.cpp:17
17              a.erase(left, size);
a=ABB left=0 right=3 size=3
```

- 位置：`04.in` 的第 3 行 `2 B`，执行到 `play(2)` 的 `a.erase` 时开始出错。
- 中间变量与定义不符：插入后 `a = "ABB"`，待消除的只有下标 1、2 的两颗 `B`，
  正确应为 `left = 1, size = 2`；实际 `left = 0, size = 3`，因为左扫描少了 `left += 1`，
  把下标 0 的 `A` 也算进了消除区间。
- **可解释性**：很好。中间变量直接违反定义（`size` 应等于 `right - left` 且只覆盖同色块），
  用一句话就能说明任务 1 的第 5 点“多删了左边一颗不同色珠子”。
- **发现难度**：低。任何“消除块左边有不同色珠子”的测例都能暴露，随机对拍 1~2 轮即可命中。

#### 3.2 代码 09：gdb + 回溯定位下溢

```text
$ gdb -q -batch -ex 'break 09.cpp:132' -ex 'run < 09.in' \
      -ex 'break 09.cpp:139' -ex 'continue' \
      -ex 'printf "len=%d plen[r.first]=%zu\n", plen[r.first]-r.second, plen[r.first]' \
      -ex 'next' -ex 'printf "plen[0]=%zu (0x%zx)\n", plen[0], plen[0]' \
      -ex 'continue' -ex 'bt 3' ./build/p09g
Breakpoint 1, play (rank=2, ch=65 'A') at 09.cpp:132
132             plen[l.first] = l.second + 1;
...
135             int len = plen[r.first] - r.second;
139             plen[r.first] = len;
len=-3 plen[r.first]=1
after plen[0]=len: plen[0]=18446744073709551613 (0xfffffffffffffffd)
Program received signal SIGSEGV
#0 __memcpy_avx_unaligned_erms ()
#1 p2a () at 09.cpp:41
#2 main () at 09.cpp:163
```

- 位置：`09.in` 的 `2 B`，执行到 `09.cpp:132` 时 `l = (0,0)`、`r = (0,4)`、`plen[0] = 5`。
- 中间变量与定义不符：`plen[0]` 先被截断成 1（只保留左侧的 `A`），
  随后 `len = plen[0] - r.second = 1 - 4 = -3`；`plen` 是 `size_t`，-3 写入后变成
  `0xfffffffffffffffd`。这个值明显不再是“块的长度”。

  这条链路看两步，但一旦看到 `plen[0]` 的负值和 `0xfffffffffffffffd` 就很直观。
- **发现难度**：低。只要消除发生在单块内部且两侧有存活珠子，1~2 轮随机对拍即可命中。

#### 3.3 代码 06 / 07：输出中间变量定位（不同于崩溃）

06 没有现成的崩溃点，用调试输出观察 `plen[0]` 和相邻行首字节：

```text
op alen=4096 pn=2 plen[0]=4095 p[1][0]=65('A')
op alen=4097 pn=2 plen[0]=4096 p[1][0]=65('A')
op alen=4098 pn=2 plen[0]=4097 p[1][0]=66('B')   <- 1 号块首字符被覆盖
```

`plen[0]` 超过 4096 时，`p[0][4096]` 实际就是 `p[1][0]`，相邻块的数据被写坏。
这解释了为什么答案在末尾几个字符处不同，也说明“块长度”这个中间变量违反了
“每块不超过 plen_bound”的不变量。

07 的调试输出：

```text
after op 3070 B: alen=2    pn=3 plen: 0 0 2
after op 0 B   : alen=-1   pn=3 plen: 18446744073709551615 0 0
```

最后一步 `alen` 变成 -1、`plen[0]` 变成 `SIZE_MAX`，说明消除区间被脏字节错误放大，
随后 `p2a` 崩溃——与 09 的下溢是同一类现象，但触发条件隐蔽得多。

#### 3.4 更简单的错例

用 `minimize.py` 从随机错例出发自动化简（删除操作 / 删除初始字符 / 合并颜色，保持错误类型不变）：

| 代码 | 随机错例规模 | 化简结果 | 与任务 1 最终测例的关系 |
| ---- | ------------ | -------- | ---------------------- |
| 04 | 19 字符 + 4 次操作 | `AB / 1 / 2 B`（2 字符 + 1 次操作） | 与最终测例相同 |
| 09 | 4 字符 + 14 次操作 | `ABA / 1 B / 3 B`（3 字符 + 2 次操作） | 与 `ABBA / 1 / 2 B` 规模同为 5，模式相同 |
| 08 | 4 字符 + 14 次操作 | 无法化简（删除任一操作都会破坏连锁结构） | 手工化简到 `ABBAA / 1 / 1 B`（5 字符 + 1 次操作） |
| 10 | 4 字符 + 14 次操作 | `ABAB` + 3 次操作 | 手工化简到 `BAA / 2 次操作`（2 字符 + 2 次操作） |

说明：

- 04 的化简非常顺利，最终只剩 2 个字符和 1 次操作，直观说明“左边界多算一个字符”。
- 09 的最小规模是 5（字符数 + 操作数），`ABA / 1 B / 3 B` 和 `ABBA / 1 / 2 B` 只是两种等价形态：
  前者先构造出单块内的消除，后者一步到位。
- 08 的自动最小化没有进展，是因为每次删除单条操作都破坏了“先消一次再连锁”的结构；
  手工构造的 `ABBAA / 1 B` 更小，说明自动最小化只能作为辅助，仍需要人理解错误模式，
  才能从一个“能失败的测例”改造成“最小的失败测例”。
- 10 手动保留第二次操作，是因为第一次操作后 `p2a` 拷贝 0 字节、全局缓冲区 `a` 里还残留着
  输入的首字符，错误被“掩盖”了；第二次操作才让错误的块长度真正体现在输出上。
  这也提醒：**对拍比较的是程序输出，而不是内部状态**，某些错误需要两次操作才能显形。

#### 3.5 复现方式

```bash
# 编译
g++ -O2 -std=c++17 -o build/base base.cpp
for i in 01 02 03 04 05 06 07 08 09 10; do
    g++ -O2 -std=c++17 -o build/p$i $i.cpp
```
